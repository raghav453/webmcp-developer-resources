# How to select a resource without copying stale code

For every tutorial or package record its source type, review date, supported entry point, setup, license and verification scope. Reject recommendations whose advertised job cannot be reproduced or whose product status is unclear.

| Question | Strong evidence | Weak signal |
| --- | --- | --- |
| Is the API current for my runtime? | Dated IDL plus actual feature test | Recent article title |
| Does the example execute tools? | Discovery and invocation trace with expected result | Animated button or tool-shaped object |
| Is it reusable? | Clear license, source, setup, negative tests | Copyable snippet with no provenance |
| Is it maintained? | Reviewed compatibility record and meaningful changes | Star count or dependency bot traffic alone |
| Is it safe? | Access and confirmation tests with limitations | “Secure by default” marketing |
| Does it solve my task? | Bounded action with useful result and errors | Generic list of browser-agent terms |

Use official specifications for interface claims and browser documentation for implementation setup. Community resources can offer original workflows or integrations; inspect the code and verify the claimed path. Vendor material is useful when it clearly separates education, working tools and planned capabilities.

Before adding a resource here, explain the reader's next step in one sentence. If it only repeats an existing guide, prefer improving the annotation or owning document. Maintain a short curated set rather than maximizing link count.
